# Supabase privacy and pairing status

This backend is not wired into the local-first app. Nothing here connects to or deploys a Supabase project. The original migration is retained for upgrade compatibility; its policies are **not safe on their own**. Apply the later hardening migration before allowing client access.

## Enforced behavior after all migrations

- Assessments, progress, journals and check-ins default to `private`. Safety settings and safety screens are owner-only.
- `shared_summary` is deliberately **not implemented**: partners cannot read summary-level progress/check-ins or any assessment rows/summaries. `partner_assessment_summaries` remains as an empty compatibility view. Owner-supplied `shared_scores` are untrusted arbitrary JSON and are never exposed to a partner, even for `shared_full` assessments. Do not report summary sharing as working.
- Only an explicit `shared_full` selection for progress, check-ins or journals while paired makes the **entire row** visible to that specific active couple. It is not a sanitized summary: answers, exercise data, journal prompt and ciphertext are included. Editing a shared row may reveal the edited content to that same partner. Full journal visibility does not provide a decryption/key-sharing mechanism.
- Old shared rows are not automatically authorized by the upgrade or for a later partner. Sharing chosen while unpaired also has no recipient. After pairing, the owner must explicitly change a selected row away from `shared_full` and back to `shared_full` to authorize it for the current couple. Simply editing the row or its internal binding cannot do that. A `shared_full` visibility value by itself therefore does **not** prove that a current partner can read the row; the app must not display it as such without implementing a trustworthy status/consent flow. Unlink ends server-side partner access, but cannot recall data already downloaded.
- A pair can collaborate on conversation-session state; the creator must be the authenticated user and session identity cannot later be rewritten. The database does not validate arbitrary text such as `guide_id` as free of sensitive content.
- Invite codes are long random secrets, expire in seven days, are single-use, and replacement revokes prior codes. Pairing and unlinking revoke outstanding invitations for both participants. Strong codes do not replace secure delivery, abuse/rate limiting, monitoring or an informed consent UI; those remain deployment prerequisites. There is no standalone revoke RPC: issuing a replacement or unlinking revokes outstanding codes.
- Pairing RPCs serialize participant mutations and a unique active-membership key prevents multiple active couples, including concurrent requests. Historical partner membership is not exposed to a new partner. Only trusted server/administrative code may mutate couple, membership, invitation or internal pairing tables; bypassing the RPCs can invalidate their invariants. The service role bypasses RLS and must never be shipped to clients.

## Upgrade and launch cautions

Stop client access while applying migrations. The hardening migration invalidates all outstanding old invite codes and requires existing full shares to be explicitly reauthorized. If legacy data already contains a user in multiple active couples or an active couple with more than two members, the migration **fails and rolls back**, rather than picking a partner. Until that data is safely reconciled and the migration succeeds, the old unsafe policies remain in place; keep clients blocked. This migration is not a data cleanup procedure.

The database does not prove that journal `ciphertext` was encrypted on device or implement key management. Nor does it establish a secure sharing UX, validate client-held data, prevent screenshots/offline retention, or prove safety of an actual hosted Supabase deployment, Auth setup, API grants, Realtime subscriptions, backups or service-role operations. Those require separate design and integration/security testing before launch. In particular, do not enable assessment or other summaries until a server-controlled, schema-validated allowlist and corresponding recipient-bound consent are designed and tested.

## Local regression tests

Run `bash supabase/tests/run.sh` from the repository root. PostgreSQL 16 server and client binaries must be installed and runnable by an unprivileged user. The runner ignores connection settings, initializes a new disposable cluster, disables TCP, uses a private Unix socket, and removes the cluster on exit. It never connects to an existing server or accepts a database URL. Tests cover legacy upgrades, client/anonymous privileges and RLS, summary canaries, defaults, consent on unlink/re-pair, impersonation, invite misuse, concurrent invite acceptance at repeatable read, and atomic failure on corrupt legacy membership. The Auth schema is a minimal local stub; these are not hosted Supabase integration tests.
